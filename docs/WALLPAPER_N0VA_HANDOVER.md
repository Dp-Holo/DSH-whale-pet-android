## 1. 人工桌面是什么

- 产品形态：系统**动态壁纸**（`WallpaperService`），壁纸服务跑在独立进程 `:wallpaperService`；本质是一个"角色/场景内容平台"，鹿鸣只是其中内容。
- 它不是"实时 3D 角色"，而是**预渲染视频 + 实时合成**：角色动作是离线渲染好的 USM/MP4（带 alpha 通道），运行时只做解码 + 合成。
- 内容按角色/分辨率/场景分包，按需下载（`playlist` + `triple_list` + 场景脚本 + 视频片段 + MD5 校验）。
- 2022 年的包，targetSdk 33，跑在今天的 Android 16 上仍能工作，但已长期不更新。

## 2. 技术架构（分层）

```
WallpaperService.Engine（生命周期 / 可见性 / 触摸 / offsets）
   └─ Player（播放器实现，持有执行器与 JS 状态机）
        ├─ IExecutor（播放抽象）
        │    ├─ ManaSoftSolutionExecutor（CRI Mana，USM 软解/多线程）
        │    ├─ ExoPlayerExecutor（MP4/视频）
        │    └─ 图片执行器
        ├─ JS 状态机（V8/j2v8）
        │    ├─ Java→JS：语义事件（SCREEN_LOCK/UNLOCK、OVERLAP、WAKEUP、
        │    │            SHAKE、AUDIO_DEVICE、CHARGING、POWER_CHANGE、ENDED…）
        │    └─ JS→Java：SET_CURRENT / PLAY / PAUSE / RESUME / SET_NEXT
        └─ Renderer（自研 sora-renderer）
             ├─ 场景/滤镜 Processor（YUV→RGB、Alpha/Yuva、模糊、矩阵）
             ├─ MatrixHandler（scale/translate/rotate）
             └─ Event/Monitor/Exception/Input Handler（横切）
```

关键设计：
- **事件驱动 + 内容定义迁移**：状态怎么变不由代码写死，而由内容包的 `triple_list`（`{src, event, dst, ext}`）定义；引擎只负责"发生事件 → 查表 → 切场景"。
- **多执行器抽象**：`IExecutor` 统一 `bindData/start/pause/reset/release/setSurface/renderScene`，按内容类型选后端并池化复用。
- **渲染分层**：场景（scene）与滤镜（filter）是 processor；矩阵操作独立；监控/异常/输入作为横切 handler。
- **内容包规范**：`<角色>/<分辨率>/<场景>/` + playlist + 脚本 + 三重 MD5（播放列表/脚本/迁移表）做增量失效。

## 3. 能力清单

### 3.1 通用壁纸能力（与 ROLE 无关）

| 能力 | 说明 |
|---|---|
| 可见性生命周期 | 桌面可见/被遮挡/息屏/解锁的暂停与恢复；预览态与真实壁纸可能并存 |
| 连续渲染 | GL 线程 60fps 常驻（这也是它的耗电问题之一） |
| 视频解码 | CRI Mana：软解、多解码线程、帧泵（16ms）驱动、EOF 保持最后一帧 |
| 透明合成 | USM 的 Yuva/Alpha 通道 + 矩阵滤镜，把角色叠在桌面背景上 |
| 内容热切换 | 换角色/分辨率/场景时 reload（含 V8 重建、执行器复用） |
| 事件投递 | Java→JS 的事件队列（独立 HandlerThread + V8 executeScript） |

### 3.2 ROLE（角色模式）能力

ROLE 是引擎的运行模式（jsName = `n0va`），它开启一整套"角色反应"管线：

| 信号 | 现状 | 对用户可见？ |
|---|---|---|
| 音频可视化 | 采集系统音频 FFT，但**只把"有/无声音"的布尔**发给 JS，幅度被丢弃 | 基本不可见 |
| 摇一摇 | 加速度计，判定 short/long，发 `SHAKE`/`LONG_SHAKE` | 内容有迁移边时可见 |
| 电源/充电 | `POWER_CHANGE`/`CHARGING` | 仅更新上下文，不切场景 |
| 耳机插拔 | `AUDIO_DEVICE_WORK/STOP_WORK` | 依赖内容边 |
| 锁屏/解锁 | 锁屏 5 分钟后切睡眠态；解锁恢复 | 依赖内容边 |
| 渲染变换 | `Renderer.scale/translate/rotate` | 未接任何信号 |

**关键事实**：ROLE 的"反应"完全由内容包的 `triple_list` 决定。鹿鸣的内容包没有写这些边，所以事件到了也是空转——这就是"更多功能敬请期待"的真相。**ROLE 不是没实现，是内容没喂。**

## 4. 它踩过的坑（对你最有价值的部分）

1. **播放器生命周期不能交给脚本**：它把暂停/恢复的决定权交给 JS，native 没有兜底；一枚 `SCREEN_UNLOCK` 事件丢失/乱序，就永久停在最后一帧。→ **壁纸端应让 Engine 持有生命周期，事件只做"请求"。**
2. **事件投递没有可靠性保证**：V8 未就绪时事件被静默丢弃、reload 窗口期事件全丢、`post` 失败无返回值。→ **事件要带投递计数/超时，关键状态用"可重放的状态查询"而不是一次性事件。**
3. **可见性事件语义借用**：用一个"解锁"事件表达"恢复可见"，导致语义漂移。→ **事件命名要一一对应真实语义。**
4. **常驻 60fps 渲染**：即使静态/不可见也在画（不可见时靠 GL 暂停，但可见静态时仍空转）。→ **不可见必停；可见时也优先按需渲染。**
5. **巨型类 + 静默 catch**：播放器实现 1100+ 行、执行器 1600+ 行，`catch → log` 遍地。→ **状态机、渲染、IO 分层，失败要可观测。**
6. **反篡改走死代码路径**：签名不匹配时调用一个不存在的方法，直接 JNI abort。→ **安全逻辑要优雅失败，不要自毁。**
7. **坐标/窗口假设**：悬浮窗那套"状态栏偏移校准"是 `WindowManager` 的坑；**壁纸 Surface 坐标原点就是 Surface 左上角，不存在这个偏移**，不要照抄。

## 5. 适合告诉你的 / 不适合告诉你的

### 可以给（建议照这个范围交流）

- 可观察行为与架构结论（本文第 2、3、4 节）；
- 失败模式与兼容性坑（尤其是可见性、事件可靠性、ROM 行为）；
- 接口**思想**（事件总线、执行器抽象、内容驱动迁移），不要求逐行实现；
- 性能基线（例：该机型上视频壁纸可见时单核 1.5–3%，可作为"你的预算上限"参考）。

### 不要给 / 不要用

- **反编译代码、资源、加密素材、native 库**：版权归 miHoYo；CRI Mana 是商业中间件，需授权；
- 签名校验绕过方法、改包/重签流程；
- 它的 UI/交互/文案/素材（鹿鸣的形象、动作片段）；
- 不要把它的做法当"最佳实践"——它是 2022 年的商业产品，有大量历史债，且形态（视频/内容平台）与鲸鱼娘（单张 2D 图）差异很大。

## 6. 对鲸鱼娘壁纸的具体建议（做减法）

- **不要上 V8/JS 状态机**：你的状态机是"位置/朝向/缩放/气泡"，纯 Kotlin 足够，还能单测。
- **不要上视频/序列帧**：单张静态图 + 运行时变换就能满足"游动"；要摆尾再考虑 sprite sheet。
- **不要做内容包平台**：单人自用，素材内置即可。
- **不要搞双后端同时常驻**：壁纸与悬浮窗二选一（或可见性互斥），避免两只鲸鱼娘。
- **要抄的三件事**：
  1. Engine 持有生命周期，事件只做请求；
  2. 不可见立刻停帧 + 帧率无关的 `dtScale`；
  3. 关键状态用"查询"而不是"一次性事件"（例如可见性直接读 `isVisible`，不要只依赖回调）。
- **要避的三件事**：
  1. 把暂停/恢复的决定权交给脚本；
  2. 事件静默丢弃；
  3. 在不可见时继续跑 Choreographer。

## 7. 如果一定要参考"事件驱动"模式，最小实现

```
Engine（唯一状态源）
  ├─ 可见性/尺寸/触摸 → 直接改状态（同步、可查询）
  ├─ 定时/系统事件 → 入一个带超时与计数的轻量队列
  └─ 每帧：state.step(dt) → renderer.render(frame)
```

不需要 JS、不需要内容包、不需要执行器池；事件只保留"确实会改变状态"的少数几个（亮屏/息屏/低电量/点击）。

## 8. 给编写交底的 AI 的建议模板

1. **事实**：项目现状、技术栈、关键类、已知坑、构建/发版约束、可提供的资源；
2. **问题**：只问事实性/边界性问题（像第 4 节那 12 条，是合理的）；
3. **期望产出类型**：说"需要一份架构评审 / 一个最小实现 / 一份兼容性清单"，但**不替对方定方案、不编号、不写接口**；
4. **验收标准**：由双方在评审后共同确定，交底阶段只给"约束"（如"只能 CI 构建"、"不能新增权限"）。
